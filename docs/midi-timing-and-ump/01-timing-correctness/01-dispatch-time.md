# Шаг 1.1. Корректное время dispatch

Статус: выполнено. Зависимости: нет.

## Цель

Не отправлять фазовые MIDI-события раньше их deadline, даже если новый тик появился
после снимка часов, и определить единый wrap-safe контракт сравнения 32-битного
времени.

## Контекст текущей реализации

В `src/main.cpp` цикл сейчас читает `micros()` в `nowUs`, затем вызывает
`midiClockReceiver.poll(...)` и только после этого
`transportController.process(nowUs, internalTicks.ticks())`.

Это создаёт два варианта одной ошибки:

1. Во время USB polling принимается внешний Clock с timestamp новее `nowUs`.
2. После чтения `nowUs`, но до извлечения очереди, IRQ публикует внутренний тик с
   timestamp новее `nowUs`.

`MidiDispatcher::dispatchDue()` вычисляет `elapsed = nowUs - _tickStartUs` как
беззнаковую разность. Когда `nowUs` фактически раньше начала тика, разность выглядит
огромной, phase насыщается до `PHASE_MAX`, и события текущего тика могут уйти раньше.

Затронутые файлы на момент составления задачи:

- `src/main.cpp` — порядок polling и снимка времени;
- `src/engine/transport_controller.h` — `MidiDispatcher::dispatchDue()`,
  `consumeTick()` и локальный `TransportController::isDue()`;
- `src/engine/external_midi_clock.h` — уже использует знаковую wrap-safe разность;
- `test/test_native/engine/test_transport_controller.cpp` — основные тесты dispatch;
- `test/test_native/main.cpp` — ручная регистрация новых test entry points.

## Контракт времени

Все timestamps остаются `std::uint32_t` и используют арифметику modulo 2^32.
Порядок двух моментов разрешено определять знаковой разностью только когда реальное
расстояние между ними строго меньше половины диапазона (`2^31` мкс, примерно
35,8 минуты). Этот горизонт нужно записать рядом с общим helper/API; вызывающий код
не должен сравнивать произвольные старые timestamps.

Если `nowUs` предшествует `_tickStartUs` в этом контракте, elapsed не вычисляется и
phase-события не отправляются. Равенство означает phase 0. Deadline события с фазой
`p` рассчитывается той же целочисленной моделью, которую использует dispatch; тесты
не должны вводить альтернативное округление.

## Работа

1. После `midiClockReceiver.poll()` получить свежий timestamp для
   `TransportController::process()`. Не менять timestamp, записанный receiver для
   самого внешнего сообщения.
2. Вынести минимальные wrap-safe операции времени в hardware-independent модуль или
   чётко определить единый существующий helper. Не оставлять разные неописанные
   варианты сравнения в transport и external clock.
3. Защитить `MidiDispatcher::dispatchDue()` от `nowUs`, предшествующего началу
   текущего тика.
4. Сохранить обработку тика, опубликованного IRQ уже после свежего снимка времени:
   защита dispatcher обязательна и не заменяется перестановкой строк в `loop()`.
5. Проверить места, где новый helper естественно заменяет сравнение timestamps,
   но не выполнять широкую несвязанную переработку планировщика.

## Детерминированные проверки

Обязательная регрессия: тик начинается в `100010` мкс, событие находится на 75% при
периоде `20000` мкс. `dispatchDue(100000)` не отправляет событие; deadline —
`115010` мкс.

Проверить отдельно:

- `nowUs` до начала тика, точно на начале, непосредственно перед deadline и точно
  на deadline;
- обычный ход через несколько phase-событий без изменения их порядка;
- начало тика перед `UINT32_MAX`, deadline после переполнения и обе стороны deadline;
- новый внутренний тик, появившийся после снимка времени;
- внешний Clock, принятый во время polling после снимка времени;
- отсутствие регрессии порядка Clock → события phase 0 → более поздние события.

## Готовность шага

- Регрессионный тест сначала воспроизводит раннюю отправку, затем проходит.
- Wrap-safe контракт и горизонт сравнения явно задокументированы в коде.
- Тесты покрывают обе причины появления тика новее `nowUs`, а не только новый
  порядок чтения часов в `main.cpp`.
- Сохраняется поведение транспорта и существующие тесты.
- Выполнен `make verify`.

## Реализация

- `src/engine/timestamp.h` определяет `timestampReached(nowUs, timestampUs)` и контракт
  modulo-2^32 с горизонтом сравнения менее `2^31` мкс.
- `MidiDispatcher::dispatchDue()` не вычисляет elapsed, когда timestamp dispatch
  предшествует началу тика. `TransportController` и `ExternalMidiClock` используют тот же helper.
- `src/main.cpp` читает timestamp для `TransportController::process()` после USB polling;
  timestamps входящих сообщений receiver не изменяются.
- `test_transport_controller.cpp` покрывает stale dispatch, внутренний и внешний тик новее
  snapshot, deadline до/на нём и wrap-around. Native tests не исполняют Arduino loop/USB polling,
  поэтому внешний случай проверяет тот же controller path с timestamp принятого Clock.
