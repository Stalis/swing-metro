# Шаг 1.4. Абсолютное расписание alarm

Статус: выполнено. Зависит от шага 1.3.

## Цель

Планировать внутренние тики от абсолютной временной сетки с накоплением дробной
части периода, чтобы задержка callback не прибавлялась к каждой следующей цели.
Явно определить поведение при смене BPM, Start/Stop и просроченном alarm.

## Контекст текущей реализации

`InternalTickSource` рассчитывает 24-PPQN deadlines независимо от Pico SDK и хранит
точный residue рационального периода `60'000'000 / (BPM * 24)`. Pico adapter
сопоставляет modulo-`2^32` deadline ближайшей будущей 64-bit boot-time цели Pico.
Callback не переносит сетку на своё фактическое время: он публикует назначенную цель,
измеряет свою latency отдельно и затем ставит следующий tagged request.

Start публикует один тик с текущим grid timestamp и ставит первый период. BPM change
создаёт новую generation с периодом от времени применения без публикации. Stop сперва
инвалидирует generation, затем очищает источник. Неположительный результат постановки
alarm деактивирует только совпавшую generation и сохраняется в diagnostics.

Затронутые файлы:

- `src/engine/internal_tick_source.h` — BPM, дробный период и записи тиков;
- `src/drivers/pico_internal_tick_alarm.{h,cpp}` — Pico alarm API и синхронизация;
- `src/engine/transport_tick.h` — формат записи/очередь;
- `test/test_native/engine/test_internal_tick.cpp` — hardware-independent модель;
- diagnostics API шага 1.3.

## Требуемая семантика

- Каждая следующая цель получается из предыдущей назначенной цели плюс очередной
  период, а не из фактического времени callback.
- Timestamp транспортного тика соответствует назначенной музыкальной сетке. Фактическое
  время callback хранится/измеряется отдельно и не сдвигает сетку.
- Start немедленно создаёт первый тик и новую сетку.
- Stop инвалидирует текущую сетку; старый callback после Stop не публикует тик и не
  оживляет alarm.
- Смена BPM начинает явно описанную новую сетку. Предпочтительная политика для
  текущего поведения: отменить старую цель и назначить следующий период от момента
  применения BPM, не создавать дополнительный немедленный тик.
- Просрочка не должна запускать бесконечный catch-up или неограниченный Clock burst.
  Нужно выбрать bounded policy: например, опубликовать не более одного просроченного
  тика и перепривязать следующую цель к первой будущей позиции сетки, отдельно
  посчитав пропущенные цели.
- Ошибка постановки alarm оставляет объект в определённом наблюдаемом состоянии и
  не маскируется как нормальная работа.

Если реализация выбирает иную политику BPM/overdue, её нужно сначала записать здесь
и покрыть тестами; музыкальная семантика не должна возникать случайно из API Pico.

## Реализованная политика

`InternalTickSource` хранит generation-tagged запрос следующего alarm и абсолютную
modulo-`2^32` цель. Start публикует единственный тик с timestamp Start и назначает
следующую цель; callback публикует timestamp своей назначенной цели, а фактическое
время остаётся только в diagnostics. Каждый новый deadline получается из предыдущего
с точным рациональным residue.

Смена BPM инвалидирует generation, не публикует тик, сбрасывает residue и назначает
первый новый период от времени применения. Stop инвалидирует generation до discard.
Старые callback и ошибки arm увеличивают stale-счётчики и не меняют новую сетку.
Совпавшая ошибка arm деактивирует источник; следующий Start является явным recovery.

Просроченный callback публикует только собственную цель. Все последующие цели, уже
достигнутые на момент callback (включая точное равенство), насыщаемо учитываются как
`missedScheduledTargets`; расчёт сразу переносит alarm на первую строго будущую цель.
Пара с расстоянием `>= 2^31` мкс неупорядочиваема: источник деактивирует эту сетку и
считает `outOfHorizonAlarmCallbacks`, без catch-up.

Для `D = BPM * 24`, `Q = 60'000'000 / D`, `R = 60'000'000 % D` и текущего residue
`F` один период равен `Q + (F + R >= D)`. Переход сразу через `N` периодов использует
`uint64_t`-вычисление `N * 60'000'000 + F`: частное на `D` прибавляется к deadline,
остаток становится новым `F`. Число уже наступивших целей также вычисляется закрытой
формулой, поэтому callback публикует максимум один record и не содержит catch-up
цикла. `periodUs` этого record остаётся первым номинальным периодом после его цели;
пропущенные цели не становятся скрытыми Clock attempts.

`PicoInternalTickAlarm` преобразует 32-bit deadline в ближайшую будущую 64-bit цель
от одного снимка boot time и вызывает `add_alarm_at(..., false)`. Значение `0`
(цель успела пройти) и отрицательная ошибка одинаково оставляют alarm невооружённым,
деактивируют совпавшую generation и не допускают синхронного callback внутри critical
section. Id callback проверяется до изменения текущего состояния.

## Работа

1. Отделить расчёт абсолютных deadlines и дробных периодов от Pico SDK так, чтобы
   модель полностью тестировалась native.
2. Хранить следующую назначенную цель wrap-safe способом и ставить аппаратный alarm
   на неё либо вычислять bounded delay до неё без накопления callback latency.
3. Передавать source назначенный timestamp тика и фактический callback timestamp
   согласно модели шага 1.3.
4. Реализовать зафиксированные политики Start/Stop/BPM/overdue и stale callback.
5. Проверять результат постановки и отмены настолько, насколько позволяет Pico API;
   ошибка увеличивает diagnostics counter.
6. Сохранить короткую критическую секцию. Не выполнять catch-up циклом без жёсткого
   малого бюджета и не публиковать пачку старых Clock.

## Детерминированные проверки

- При 120 BPM callback latency `10, 40, 5` не сдвигает цели
  `20'833, 41'666, 62'500`.
- Для 68, 100, 137 и 240 BPM десять тысяч периодов совпадают с целой частью идеального
  рационального времени; callback latency в сумму не входит.
- Wrap-around абсолютной цели сохраняет интервалы и порядок.
- Start создаёт ровно один немедленный тик; Stop и stale callback не создают новых.
- Смена BPM соблюдает выбранную границу новой сетки и сброс дробного accumulator.
- Большая просрочка приводит к bounded числу публикаций, учитывает пропущенные цели
  и назначает будущий alarm, а не бесконечно догоняет прошлое.
- Отказ постановки alarm наблюдаем и не оставляет `_active` в вводящем в заблуждение
  состоянии.

- Искусственная callback latency не накапливается в музыкальной сетке.
- Все переходы и overdue policy описаны и проверены независимо от оборудования.
- На устройстве diagnostics различает callback lateness и задержку main-loop
  обработки.
