# MIDI timing, регулярный ввод и подготовка к UMP

Статус: этапы 1–2, 4 и стабилизация S завершены; шаги 5.1–5.4 и аппаратные проверки
5.5.1–5.5.2 выполнены. Этап 3 аппаратно отклонил polling; bounded IRQ/PIO follow-up отложен до
переразводки энкодеров на входной shift register. Этап 6 запланирован.
Дата: 2026-09-27.

## Цели и summary

Сделать отправку MIDI предсказуемой и наблюдаемой, исправить ошибку времени и
потерю событий при отказе USB, стабилизировать считывание ввода и добавить Gate Percent для каждого шага. Подготовить
границу между музыкальными событиями и USB-кодированием для будущего перехода
на UMP и управления отдельными нотами.

Работа начинается на текущем Arduino-Pico/TinyUSB. MIDI и применение команд
остаются на ядре 0, LVGL — на ядре 1. Перенос ввода между ядрами, FreeRTOS,
Pico SDK и DMA экрана не являются обязательными этапами: необходимость таких
изменений определяется измерениями.

MPE и MIDI 2.0 не тождественны. Классический MPE использует MIDI 1.0 и отдельные
каналы для нот. MIDI 2.0 предлагает собственные per-note сообщения. JR timestamps
в UMP — отдельная опциональная возможность, применимая и к MIDI 1.0 внутри UMP.
Поддержка выразительности не доказывает поддержку timestamps; timestamps не
устраняют постоянную задержку до DAW и не гарантируют меньшую live latency.

## Отправная точка

- Аппаратный alarm публикует тики; MIDI отправляет основной цикл.
- `nowUs` читается до USB polling. Более поздний timestamp принятого тика может
  вызвать беззнаковое переполнение при вычислении elapsed и раннюю swing-ноту.
  Аналогичный порядок возможен при публикации внутреннего тика из IRQ.
- `UsbMidiPacketSink` игнорирует результат `writePacket()`; состояние нот может
  обновляться даже при отказе USB-стека принять пакет.
- Секвенсор и очередь содержат готовые USB MIDI 1.0 пакеты.
- Ввод опрашивается на каждом обороте loop; debounce зависит от числа опросов.
- `lateTicks` не измеряет величину опоздания; `lateEvents` не обновляется.
- Передача пикселей экрана синхронная. Процент полезной загрузки и максимальные
  блокировки на устройстве пока не измерены.

Это план поверх текущей реализации. Документы в соседних каталогах описывают
предыдущие этапы; при расхождении с их историческими описаниями проверить код.

## Общие ограничения

- Сохранить музыкальную семантику tick/phase, swing, Start/Stop/Continue и режимов
  clock, кроме явно описанных исправлений и новой длительности нот через Gate. Не менять swing-формулу попутно.
- По умолчанию monophonic: новый Note On глушит предыдущую ноту только если
  её Gate ещё не завершился. Прямая граница шага сама по себе ноту не обрывает.
- У секвенсора и транспорта один владелец; UI получает согласованные снимки.
- В критическом пути нет неограниченных циклов ожидания, печати, динамического
  выделения памяти и файловых операций.
- LittleFS не читается и не записывается при работающем транспорте.
- Новую независимую от оборудования логику размещать в native-тестируемых модулях;
  регистрировать тесты в `test/test_native/main.cpp`.
- Для изменений прошивки выполнять `make verify`. Native-тесты не заменяют
  аппаратную проверку timing, USB и GPIO.
- Не обещать конкретную конечную задержку или загрузку CPU до измерений.
