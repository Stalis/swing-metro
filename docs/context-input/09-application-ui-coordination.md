# Этап 9. Координация приложения, контекста и LVGL

Статус: реализовано 2026-09-12; основные функции проверены пользователем на устройстве.

## Задача для агента

Реализовать вход и выход из настроек шага так, чтобы app state, стек ввода и экран
LVGL менялись согласованно, но оставались разделены между ядрами. Добавить
`StepSettingsContext`, в котором энкодер изменяет ноту выбранного шага вместо tempo.
На настоящем устройстве проверить также глобальный Start/Stop и временный Shift:
пока их источники — кнопки энкодеров Tempo и Volume соответственно. Это временная
привязка на уровне приложения, не часть универсальной библиотеки.

  поле, необходимое этому этапу.

## Согласованное поведение экрана и нот

- `LongPressed` шага на MainDisplay открывает его настройки при достижении порога
  500 мс. В настройках `Pressed` другого шага сразу переключает выбор, меняя
  выбранный шаг внутри уже существующего контекста. Последующие фазы этого
  удержания не закрывают настройки. Повторное долгое нажатие **выбранного** шага
  закрывает настройки; `Clicked` и `LongPressed` другого шага также могут выбрать
  его, если `Pressed` произошёл ещё до открытия экрана.
- `Clicked` шага на главном экране включает/выключает его. В настройках нажатие
  другого шага выбирает его для редактирования, не меняя состояние включения;
  короткое нажатие уже выбранного шага поглощается без действия. `Released` сам
  по себе шаг не переключает.
- Энкодер Tempo в настройках меняет MIDI-ноту выбранного шага на `delta`
  полутонов. Диапазон — 36–127 включительно, что в текущем соглашении проекта
  обозначается C0–G7; на границе применяется clamp, не wrap.
- Повороты Swing и Volume в настройках пока поглощаются без изменения параметров.
  Кнопки этих энкодеров — отдельные источники и описаны ниже.
- У `Sequencer` уже есть `SequencerStep::note`, но нет безопасного API для чтения
  и изменения произвольного шага. Добавить минимальные методы с проверкой индекса
  и арифметикой без переполнения; универсальные типы `ContextInput` не менять.

## Единственный владелец навигации

`ContextInput` и LVGL не синхронизируют друг друга напрямую. Операция уровня
приложения является единственным владельцем перехода:

```text
handle OpenStepSettings{N}
  1. validate N
  2. store selected step N
  3. add StepSettingsContext
  4. publish desired page + selected step through UiViewModel
```

Выход выполняется симметрично:

```text
handle CloseStepSettings
  1. release StepSettingsContext
  2. clear or preserve selected step according to app-state contract
  3. publish MainDisplay page through UiViewModel
```

Если добавление контекста завершилось `StackFull`, приложение не должно публиковать
экран, ввод для которого не активирован. Если публикация состояния имеет отдельную
ошибку, переход должен остаться согласованным; конкретный простой порядок операций
и rollback описать в коде и тестах.

Сейчас `AppEventHandler` хранит один отложенный `OpenStepSettings` без источника.
В этом этапе заменить его немедленной обработкой смыслового события на app-level
границе после `dispatch()`: для изоляции жеста нужно знать `InputId` кнопки,
инициировавшей переход. Старый pending API и соответствующие тесты обновить,
не оставляя двух конкурирующих владельцев навигации.

## События жеста, вызвавшего переход

Согласованное дополнительное требование: если контекст был добавлен из-за события
кнопки, остаток **того же физического нажатия** не должен случайно выполнить действие
во вновь добавленном контексте. Например, `Pressed` открыл экран, а последующий
`LongPressed` или `Released` этой же кнопки уже поступает после смены стека.

Один вызов `Router::dispatch()` обрабатывается целиком на прежнем стеке: приложение
добавляет контекст только после возврата результата, поэтому исходное событие не
переигрывается. Но `ButtonInputAdapter` создаёт отдельные события `Pressed`,
`Clicked`, `LongPressed`, `Released` в ходе одного удержания. Изоляция **следующих**
событий этого же жеста пока не реализована и должна быть спроектирована здесь на
app-level границе. Нельзя полагаться только на то, что `Clicked` и `LongPressed`
взаимоисключающие: `Released` всё равно придёт, а переход может начаться уже по
`Pressed`.

Перед реализацией выбрать и описать простое правило владения жестом: например,
запоминать source открывшей кнопки до её `Released` и подавлять оставшиеся фазы
для нового контекста, либо откладывать активацию нового контекста до завершения
жеста. Правило должно быть совместимо с независимыми одновременными кнопками и не
блокировать ввод остальных источников. Не добавлять скрытый capture в универсальный
`Router` без отдельного обоснования: сейчас он маршрутизирует каждый `InputEvent`
независимо и не знает границ физического жеста.

Принятое для этого этапа правило: app-level координатор запоминает источник
кнопочного события, изменившего навигационный контекст, в хранилище фиксированной
ёмкости. Все последующие фазы этого источника не направляются в новый стек вплоть
до `Released` включительно; затем запись очищается. Сырые диагностические строки
Serial могут показывать эти фазы, но смыслового действия от них не будет.

После `LongPressed` должен сохраняться ожидаемый переход к настройкам шага, но
`Released` открывшей кнопки не должен выполнять действие нового экрана. Если
переход когда-либо будет инициирован по `Pressed`, последующий `LongPressed` того
же удержания также не должен влиять на новый контекст.

## Разделение ядер

- Основной `loop()` владеет ContextInput, app state, секвенсором и обработкой ввода.
- `loop1()` владеет LVGL и читает согласованный снимок `UiViewModel`.
- Контекст не вызывает `lv_screen_load()` и не хранит `lv_obj_t*`.
- LVGL callbacks не вызывают `addContext()` или `releaseContext()` с другого ядра.
- В снимок UI добавляется минимальное состояние: идентификатор страницы, выбранный
  шаг и отображаемые параметры этой страницы.

Использовать существующий механизм публикации snapshot. Не вводить новый event bus
или RTOS только для навигации.

В `UiViewModel` страница, выбранный шаг и отображаемая нота должны читаться
согласованно. Текущие два атомарных слова не дают цельного снимка всего
`UiSettings`; при расширении предусмотреть версионированную публикацию через
атомарные поля и читать её до устойчивой версии. Публиковать при изменении
состояния, чтобы `loop1()` не застревал в повторном чтении. Второй LVGL-экран
создать один раз в `setup1()`, а переключать и обновлять его только из `loop1()`.

## StepSettingsContext

Контекст хранится приложением и добавляется поверх `MainDisplayContext`.

Минимальный согласованный пример:

```text
TempoEncoder + turn(-1/+1) -> AdjustNote{-1/+1}
```

Смысловой `AdjustNote` означает изменение на один полутон. Приложение применяет его
к выбранному шагу с явно определёнными min/max или политикой wrap. Сам контекст не
знает текущую ноту и не изменяет шаг.

Остальные энкодеры либо получают явно согласованные действия Step Settings, либо
контекст возвращает `consume()` для их вращения, чтобы ввод не провалился в
`MainDisplayContext` и случайно не изменил swing/volume. Не оставлять этот выбор
неявным.

`StartStop` из будущего/существующего `GlobalContext` должен по-прежнему проходить
вниз, если `StepSettingsContext` его не обрабатывает.

## Shift и дополнительные контексты

Навигационный контекст и Shift независимы:

```text
GlobalContext -> MainDisplayContext -> StepSettingsContext -> ShiftContext
```

`releaseContext(shiftContext)` работает по идентичности объекта и не должен удалить
StepSettings. Закрытие StepSettings также не должно неявно очищать весь стек.

### Временная аппаратная привязка Start/Stop и Shift

Кнопки на энкодерах рассматриваются как **отдельные источники ввода**; поворот
энкодера не меняет SourceId и не зависит от его кнопки. Для этого этапа:

- Кнопка Tempo — Start/Stop. Её debounced `Pressed` через app-level кнопку/адаптер
  превращается в одно `ToggleTransport`, обрабатываемое нижним `GlobalContext`
  независимо от открытого экрана и Shift. Остальные фазы не переключают транспорт,
  поэтому удержание не создаёт повторных переключений.
- Кнопка Volume — удерживаемый Shift. Debounced press/release передаются в
  `TriggerInputAdapter` как `active=true/false`. После возврата `dispatch()`
  приложение добавляет или удаляет заранее созданный `ShiftContext` по
  идентичности объекта. На этом этапе Shift **не переназначает** энкодеры и
  кнопки: проверяются реальное добавление/удаление контекста и его состояние,
  видимое в Serial. Верхние контексты обязаны пропускать событие выключения Shift
  к нижнему обработчику. Другие источники работают как прежде.
- Кнопка Swing остаётся без нового действия.

Сейчас `Encoder::switchHandler` вызывается только на debounced нажатии. Поэтому
добавить минимальный совместимый способ получить также debounced отпускание
кнопки, не меняя декодирование поворота и существующий callback нажатия.
`Encoder` не должен знать о Start/Stop, Shift, `InputId` или контекстах.
В будущем физические Start/Stop и Shift заменят только привязку источников в
`main.cpp`; смысловые события и обработчики сохранятся.

Секвенсор сейчас работает непрерывно. Start/Stop добавляет явное состояние
воспроизведения: при остановке новые шаги и Note On не создаются, звучащая нота
получает один Note Off; при запуске временная база синхронизируется заново.
Начальное состояние остаётся «запущено», как сейчас. MIDI transport-сообщения и
новые музыкальные функции в этот этап не входят. Состояние выводится в Serial
для аппаратной проверки.

## Тесты

1. OpenStepSettings с валидным N добавляет ровно один контекст и публикует страницу.
2. Невалидный N не меняет ни стек, ни UI state.
3. Повторное открытие не дублирует контекст.
4. Закрытие удаляет точный контекст и возвращает MainDisplay.
5. Tempo encoder на MainDisplay создаёт AdjustTempo.
6. Тот же энкодер в StepSettings создаёт AdjustNote.
7. Неиспользуемый в StepSettings энкодер не проваливается вниз, если выбран consume.
8. Глобальное событие проваливается до нижнего контекста.
9. Shift добавляется и удаляется независимо от StepSettings.
10. UiViewModel публикует согласованный snapshot для второго ядра.
11. Release кнопки после LongPressed не вызывает ToggleStep в новом контексте.
12. Кнопка, открывшая контекст по Pressed, не вызывает в нём действие своим
    последующим LongPressed/Released.
13. Кнопка, открывшая контекст по LongPressed, не вызывает в нём действие своим
    Released; другая одновременно удерживаемая кнопка продолжает работать.
14. Кнопка Tempo переключает транспорт ровно один раз за нажатие на MainDisplay,
    в StepSettings и при активном Shift; удержание не повторяет команду.
15. Остановка отправляет один Note Off для звучащей ноты, не создаёт новых нот;
    запуск восстанавливает ход секвенсора без скачка накопленного времени.
16. Кнопка Volume добавляет Shift только после debounced press и удаляет после
    debounced release, в том числе если между ними открыт или закрыт StepSettings.
17. Кнопка Swing не получает нового действия, а замена аппаратного источника
    Start/Stop или Shift не требует изменений в универсальном `ContextInput`.

## Аппаратная проверка

- Long press Step N открывает настройки именно N.
- На главном экране короткое нажатие шага переключает его включение.
- В настройках нажатие другого шага сразу переключает экран на его настройки,
  не меняя состояние включения ни одного шага и не добавляя новый контекст.
- Долгое нажатие выбранного шага закрывает настройки и удаляет контекст из стека.
- Поворот выбранного энкодера меняет ноту по полутонам: C0 -> C#0 и обратно.
- Выход восстанавливает исходное назначение энкодера.
- Кнопка Tempo запускает/останавливает секвенсор на обоих экранах и под Shift;
  Serial показывает ровно один переход на нажатие.
- Удержание кнопки Volume включает Shift, отпускание выключает его; Serial
  показывает обе границы, остальные органы управления не меняют семантику.
- Кнопка Swing сохраняет прежнее поведение.
- UI и ввод не расходятся при быстрых повторных переходах.

## Критерии готовности

- App state является единственным владельцем перехода.
- LVGL и ContextInput не зависят друг от друга.
- Межъядерная граница проходит через UiViewModel snapshot.
- Один энкодер имеет разную смысловую семантику в двух контекстах.
- Ошибка добавления контекста не оставляет ложный экран.
- Последующие фазы жеста, открывшего контекст, не действуют на новый контекст.
- Временные аппаратные привязки Start/Stop и Shift изолированы в приложении;
  для переноса на отдельные кнопки не нужно менять универсальную библиотеку.

## Передача результата

### Фактическая модель и порядок перехода

`AppInputCoordinator<Capacity>` в `src/input/app_input_coordinator.h` владеет
заранее созданными `GlobalContext`, `MainDisplayContext`, `StepSettingsContext`,
`ShiftContext` и ограниченным `Router`. `dispatch(input, nowUs)` выполняет один
проход по текущему стеку, затем `handleAppEvent()` применяет смысловой результат.
Координатор хранит выбранный шаг как `std::optional<uint8_t>`; отсутствие шага
соответствует главному экрану. Старый однопозиционный
`AppEventHandler::takeOpenStepSettingsRequest()` удалён: запрос теперь
обрабатывается сразу после `dispatch()` вместе с исходным `InputId`.

Открытие проверяет `step < 16` и свободную ёмкость стека. Только после успешного
`addContext(stepContext)` сохраняется шаг, который затем попадает в снимок UI.
При `StackFull` экран и выбранный шаг остаются прежними. При открытии поверх
удерживаемого Shift он временно удаляется и сразу возвращается поверх
`StepSettingsContext`, сохраняя порядок стека. Закрытие удаляет точный
`StepSettingsContext` по идентичности и очищает выбранный шаг, не затрагивая
Shift. Повторный запрос другого шага меняет выбор без второго контекста.

Источники кнопок, вызвавших навигационный переход, отмечаются в фиксированном
`std::bitset<256>`. Следующие фазы этого же удержания не маршрутизируются;
`Released` тоже подавляется и снимает отметку. Другие кнопки продолжают
работать. Переход, инициированный уже на `Released`, не оставляет отметку.
Диагностический Serial-вывод сырых фаз матрицы сохранён.

### Нота, транспорт и временные кнопки

`Sequencer::getStepMidiNote(index)` и `adjustStepNote(index, delta)` проверяют
индекс. Нота изменяется на полутон с clamp в MIDI 36–127; текущая нота
выбранного шага публикуется для экрана. `StepSettingsContext` превращает
`TempoEncoder` в `AdjustNote`, а повороты Swing/Volume поглощает. В настройках
`Pressed` другого шага сразу меняет выбранный шаг в уже существующем
`StepSettingsContext`; дальнейшие фазы этого же удержания подавляются до
`Released`. Короткое нажатие уже выбранного шага поглощается. Включение шагов
по клику осталось только на главном экране.

`EncoderSettings::switchReleaseHandler` добавляет отдельный совместимый callback
debounced отпускания. Поворот и старый `switchHandler` не менялись.
В `main.cpp` кнопка Tempo создаёт события через `ButtonInputAdapter`:
только `Pressed` превращается в `ToggleTransport`; долгий press и release не
переключают транспорт повторно. Кнопка Volume передаёт debounced press/release
в `TriggerInputAdapter`; `GlobalContext` выдаёт `ActivateShift`/
`DeactivateShift`, после чего координатор добавляет/удаляет заранее созданный
ShiftContext. Shift пока пропускает все остальные события без переназначения.
Кнопка Swing сохраняет прежний Serial-вывод и не подключена к контекстам.

Секвенсор запускается работающим, как прежде. Stop запрещает новые шаги и
Note On; при наличии звучащей ноты `main.cpp` посылает один Note Off.
Start сбрасывает временную базу через `sync(micros())`, затем ход начинается
с шага 0 на следующей доле. Serial выводит `[Transport] Start/Stop` и
`[Shift] Active/Inactive`. MIDI Start/Stop-сообщения не отправляются.
После `sync()` внутренний индекс временно равен 15 для расчёта следующего шага,
но `Sequencer::getDisplayStepIndex()` возвращает `nullopt` до первого реального
`update()`. В `UiViewModel` это кодируется как `activeNote = UINT8_MAX`:
дисплей не подсвечивает последний шаг перед первым шагом 0. Тайминг и MIDI
при этом не меняются.

### UI и проверки

`UiSettings` содержит `UiPage`, выбранный шаг, его MIDI-ноту и состояния
transport/Shift. `UiViewModel` публикует фиксированные атомарные поля с
версионированием; чтение повторяется, если публикация пересеклась с ним.
Одинаковые снимки не перепубликуются. `LVGL_Ui` заранее создаёт второй экран
с надписями шага (1–16) и ноты (C0–G7), а переключает экраны и обновляет
надписи только на ядре `loop1()`. `ContextInput` не зависит от LVGL.

- `make format` и полный `make verify` прошли: `clang-format`, `clang-tidy`,
  113 из 113 native-тестов и сборка прошивки `rpipico2`.
- Новые native-тесты проверяют навигацию, StackFull, изоляцию фаз удержания,
  независимость двух кнопок, назначение энкодеров, Shift, Start/Stop, пределы
  ноты и согласованное чтение UI-снимка из другого потока. Отдельный
  регрессионный тест проверяет: открыть первый шаг, кликнуть третий, получить
  выбранный индекс 2 без включения третьего шага, а затем редактировать его ноту.
  Ещё один тест проверяет смену выбора непосредственно на `Pressed`, неизменный
  размер стека и удаление контекста после закрытия.
- Пользователь подтвердил работу этапа на устройстве, включая Shift и
  Start/Stop. До этого пользователь заметил кратковременную подсветку шага 15
  сразу после Start; исправление внесено после этой проверки и ещё не
  подтверждено на устройстве. Исправление короткого нажатия в настройках
  и переключения на `Pressed` также прошло автоматические проверки, но ещё не
  проверено на устройстве.
  Точный MIDI Note Off при остановке отдельно не подтверждён.
