# Введение и архитектурные инварианты

Статус: согласовано.

## Цель

Создать в `lib/ContextInput` универсальную C++17-библиотеку, которая принимает
нейтральные события от физических или программных источников, пропускает их через
ограниченный стек контекстов и возвращает смысловые события приложения.

Пример одного и того же входа:

```text
MainDisplayContext + TempoEncoder + turn(+1)  -> AdjustTempo{+1}
StepSettingsContext + TempoEncoder + turn(+1) -> AdjustNote{+1}
```

Источник может быть энкодером, отдельной кнопкой, матрицей, MIDI, тестом или
программным компонентом. Ядро библиотеки не должно различать аппаратные и
программные источники.

## Поток данных

```text
hardware/software source
          |
          v
optional source adapter
          |
          v
      InputEvent
          |
          v
ContextInput::Router<InputEvent, AppEvent, Capacity>
          |
          +-- top context: handle or pass
          +-- next context: handle or pass
          +-- bottom context: handle or pass
          |
          v
 DispatchResult<AppEvent>
          |
          v
 application event handler -> model / sequencer / UiViewModel
```

`ContextInput` возвращает результат вызывающему коду. Он не хранит callback
приложения и не вызывает доменные объекты напрямую.

## Что такое контекст

Контекст — обычный пользовательский объект, интерпретирующий `InputEvent`.
Контекст не обязан соответствовать экрану. Примеры:

- `GlobalContext` — Start/Stop и другие глобальные команды;
- `MainDisplayContext` — обычное управление главным экраном;
- `StepSettingsContext` — редактирование выбранного шага;
- `ShiftContext` — временное переназначение элементов управления;
- модальный контекст — обработка или блокировка ввода поверх экрана.

Пример стека, где последний добавленный контекст находится сверху:

```text
top     ShiftContext
        StepSettingsContext
        MainDisplayContext
bottom  GlobalContext
```

Событие передаётся сверху вниз. Первый результат, отличный от `Unhandled`,
останавливает обход. Благодаря этому глобальная кнопка может провалиться до
`GlobalContext`, а модальное окно может намеренно поглотить ввод.

## Инварианты реализации

- Код компилируется как C++17; concepts не используются.
- Параметры шаблонов, обозначающие типы, именуются с префиксом `T`: например,
  `TInputEvent`, `TOutputEvent`, `TContext` и `TSourceId`.
- В ядре нет зависимости от Arduino, GPIO, LVGL, Sequencer или Swing Metro.
- Нет `new`, `delete`, `std::vector`, `std::list`, `std::function` и скрытого heap.
- `std::array`, `std::optional` и `std::variant` допустимы: они имеют фиксированное
  размещение и не выделяют память динамически.
- Ёмкость стека задаётся параметром шаблона.
- Объекты контекстов принадлежат приложению и должны жить всё время нахождения в
  стеке; библиотека хранит только невладеющие ссылки.
- Один вход создаёт не более одного смыслового события. Расширение до фиксированного
  пакета событий обсуждается отдельно, только если появится реальный сценарий.
- Ядро однопоточное. Все операции со стеком и `dispatch()` выполняются на ядре,
  обрабатывающем ввод. Передача данных в LVGL на другом ядре идёт через состояние
  приложения, а не через прямой вызов GUI.
- Изменение стека выполняется после возврата из `dispatch()`, при обработке
  смыслового события приложения. Контекст не модифицирует маршрутизатор из `handle()`.
- Необработанное событие является нормальным результатом, а не ошибкой.

## Разделение ответственности

| Компонент | Ответственность | Не отвечает за |
| --- | --- | --- |
| `Encoder` | GPIO и декодирование поворота | Контекст и смысл поворота |
| `ButtonState` / `ButtonMatrix` | Сканирование и debounce | Навигацию и действия приложения |
| Адаптер | Перевод интерфейса источника в `InputEvent` | Выбор смыслового действия |
| Контекст | Интерпретация события на своём слое | Изменение модели и отрисовку |
| `ContextInput` | Хранение стека и порядок dispatch | Владение контекстами и событиями приложения |
| Приложение | Применение `AppEvent`, изменение стека и UI state | Декодирование GPIO |
| LVGL | Отображение опубликованного состояния | Владение стеком ввода |

## Начальное состояние репозитория

- Активная ветка: `feature/contextual-input`.
- Каркас библиотеки: `lib/ContextInput/library.json` и
  `lib/ContextInput/src/context_input.h`.
- Интерфейс энкодера: `lib/Encoder/src/encoder.h`.
- Состояние кнопки и матрица: `lib/ButtonMatrix/src/button_state.h` и
  `lib/ButtonMatrix/src/button_matrix.h`.
- Текущая прямая обработка ввода: `src/main.cpp`.
- LVGL работает в `setup1()` / `loop1()`, а ввод — в основном `loop()`.
- Native-тесты находятся в `test/test_native`.

Агент обязан сверять этот список с текущим деревом: документы этапов отражают
целевой порядок, а не гарантируют, что предыдущий этап уже выполнен.

## Целевая структура библиотеки

Имена могут уточняться внутри этапа, но ответственность файлов сохраняется:

```text
lib/ContextInput/
  library.json
  src/
    context_input.h
    context_input.ipp
    input_event.h
    dispatch_result.h
    context_ref.h
    adapters/
      encoder_input.h
      button_input.h
      trigger_input.h
```

Шаблонные определения остаются в заголовке или подключаемом `.ipp`, как уже
сделано для `ButtonMatrix`. Пустые `.cpp` и заранее созданные неиспользуемые модули
не добавляются.
