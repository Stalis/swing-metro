# 16 simultaneous programs and MIDI routing — planned

The current `Session` has one `Playback`, one `TransportController`, one delivery queue and channel 1 output. The target is up to 16 independently positioned playbacks under **one** master transport, tempo, internal/external clock and delivery stream. Each program gets a 16-bit MIDI-channel mask; sets may overlap. A program may target several or all 16 channels, and several programs may target the same channel. UI numbers are 1–16, MIDI packet channel values 0–15. Proposed zero mask means mute while musical position continues; confirm in product design.

Each playback needs its own program reference/snapshot, cursor and generation. Event identity must distinguish at least session generation, track identity/generation, launch, channel and pitch. Fan-out from one musical attack creates a distinct delivery obligation per channel; retry must not duplicate a channel already accepted. Stop of one track releases only its accepted notes; global Stop releases all. A route edit first releases notes on old channels and applies the new mask at a safe boundary. A stale Off from an old generation must never terminate another track's new launch.

MIDI itself carries channel and note, not track identity. Two simultaneous equal-pitch notes on the same channel cannot be independently identified by an external receiver. The R5 contract selects **retrigger per party**: each party sends its own On and Off; the receiver determines how overlapping Off messages sound. Internal ownership and generations still prevent one party's stale Off from being mistaken for another party's lifecycle event. The UI and documentation must explain that independent sounding holds cannot be guaranteed on every receiver. Coalescing by `(channel, note)` would suppress retriggers and alter the agreed load; changing to it needs a separate product decision. Tests must cover internal accounting and the actual wire packet order.

## Capacity and measured feasibility

The R5 production queue holds 16 events, permits eight packets per tick, and the dispatcher attempts at most eight sends per pass. These limits cannot cover the maximum fan-out as-is. At 16 tracks × 16 channels × 16 repeat attacks × two note packets, the theoretical upper bound is 8,192 note packets per sixteenth. At 240 BPM (16 sixteenths/s), that is 131,072 packets/s or 524,288 bytes/s before USB overhead. Even without Repeat, one common boundary can produce 256 Note On packets.

R5 measured only the real `UsbMidiMessageSink::send()` / `writePacket()` path on a Pico 2 W: 131,072/131,072 packets accepted by the USB stack in a one-second spike; 12,402 RetryLater results; maximum acceptance lateness 4,773 µs, within the user-revised 5 ms gate by 227 µs. 89,844 packets were accepted over 1 ms late. The probe excluded the engine queue, UI, Clock and host receipt, so it is a lower-bound sink test, not proof that 16-program playback meets timing. See [R5 evidence](../refactoring/r5-composition-result.md).

Before shipping, measure a full device under internal/external Clock, GUI load and host capture. Track queue high-water, dropped/expired events, Clock lateness, loop duration, USB retry and actual host receipt. Stream route/repeat expansion rather than pre-enqueueing the full worst case; reserve Off capacity for accepted notes, define admission/overload behavior, and size bounded buffers from measurements. Do not silently discard required notes when the promise cannot be met.

Acceptance: 16 programs to one channel, to disjoint channels and to all channels; partial overlaps, same pitch and differing velocity with per-party retriggers; independent lengths 3/5/16; per-track/global Stop and route edit; one outgoing Clock; partial fan-out retry; disconnect/relock and overload with safe note release. Repeat maximum and receiver behavior under overlaps remain release gates.
