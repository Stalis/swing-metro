# Диагностика Swing Metro

Live-сборщики поддерживают только `swing_metro_diagnostics_v4`. Старые v2/v3,
неизвестные версии, неверное число колонок и нецелые значения данных отклоняются.
Формат v4, порядок колонок и значения отчёта сохранены относительно R0.

## Протоколы и сборщики

| Протокол | Назначение |
| --- | --- |
| `swing_metro_control_v1` | Команды и состояние RUN/EXTERNAL_RUN |
| `swing_metro_diagnostics_v4` | Tick pipeline, доставка, очереди, сессия, распределения lateness |
| `swing_metro_input_diagnostics_v1` | Накопленные метрики опроса энкодеров |
| `swing_metro_runtime_diagnostics_v1` | Окно LVGL/display/encoder timing |
| `swing_metro_fault_v1` | Выбор fault-сценария, только в соответствующей сборке |
| `swing_metro_timed_run_report_v1` / `swing_metro_fault_run_report_v1` | Итоговые JSON-отчёты |

Версия каждого протокола независима: актуальные v1 не являются устаревшей диагностикой.
`scripts/pico_serial_run.py` собирает serial-only измерения;
`scripts/pico_midi_run.py` дополнительно записывает MIDI на компьютере. Оба используют
один разборщик `pico_run_protocol.py` и `TimedRunCapture` из `pico_run_report.py`.
Параметры запуска: `python scripts/pico_serial_run.py --help` и
`python scripts/pico_midi_run.py --help` в окружении проекта.

## Жизненный цикл

Команды: `RUN <ms> <bpm> <swing>` и `EXTERNAL_RUN <ms> <bpm> <swing>`.
Допустимы 1000–3600000 ms, 40–240 BPM и swing в поддерживаемом прошивкой диапазоне.
Команда принимается при остановленном секвенсоре, без незавершённого прогона или
ожидающей выгрузки диагностики.

1. RUN применяет tempo/swing, включает внутренний режим, печатает `run_started`,
   завершает отправку Serial и запускает транспорт.
2. EXTERNAL_RUN требует внешнего режима. Перед `run_started` ждёт подтверждённый
   снимок второго ядра и сбрасывает окно энкодеров; сам транспорт не запускает.
3. По истечении времени внутренний RUN останавливает транспорт. Для внешнего
   прогона внешний источник должен заранее остановить транспорт; иначе выдаётся
   `external_transport_still_running`, без успешного `run_complete`.
4. После остановки запрашивается снимок второго ядра. Только при остановленном
   транспорте и готовом снимке выводятся три диагностические строки. Заголовки
   выводятся перед ними один раз за время работы прошивки.
5. `run_complete` выводится один раз, после остановки alarm и завершения выгрузки.

Смена внешнего режима во время прогона даёт `external_mode_changed_during_run`.
Сборщик проверяет порядок, параметры, единственность строк и полноту набора;
заголовок не считается измерением. Не выполняйте LittleFS-операции во время playback.

## Владельцы кода

- `src/input/serial_run_controller.{h,cpp}` — команды и состояние прогона;
  переносимая логика, зависимости передаются явно.
- `src/engine/diagnostics_capture.h` — запрос/подтверждение снимка второго ядра,
  ожидание остановки, владение ожидающей выгрузкой.
- `src/engine/diagnostics_serializer.{h,cpp}` — wire-format и порядок значений.
- `src/engine/diagnostic_output.h` — минимальный текстовый выход сериализатора.
- `src/drivers/diagnostics/arduino_diagnostic_console.h` — Serial и часы Arduino.
- `src/application.{h,cpp}` — связывает объекты и сохраняет порядок loop: приём команды,
  MIDI/transport/input, обновление прогона, alarm, выгрузка, завершение, UI/storage.
  `src/main.cpp` только делегирует четыре Arduino entry points объекту `Application`.

LVGL остаётся на втором ядре; его снимки передаются через прежний атомарный API.
Сборки production, instrumentation-off и fault остаются отдельными. В режиме off
схема v4 сохраняется, отключённые поля инструментирования заполняются нулями.

## Как читать метрики

Attempt — попытка отправки устройством; accepted — принятие USB-стеком; host-observed —
получение на компьютере. Это разные события. Времена устройства и host относятся к
разным часам и не вычитаются для оценки end-to-end latency.

Накопленные с загрузки счётчики не становятся метриками одного прогона автоматически.
Сводка сохраняет `not_comparable_cumulative_firmware_counters`, когда сравнение
невозможно. Исходная семантика `tick_queue_overflows` (исторический alias
`failed_publications`) сохранена; отдельное поле `internal_tick_queue_overflows`
содержит соответствующий счётчик очереди.

## Проверки и старые данные

`make test-scripts` проверяет v4-only parsing, отказ старых схем и воспроизведение
исторического отчёта. `make test` проверяет C++-сериализацию по замороженным заголовкам,
последовательность RUN/EXTERNAL_RUN, ожидание core 1 и завершение после выгрузки.
`make verify` дополнительно проверяет форматирование, clang-tidy и три сборки.

[R0 fixtures](../scripts/tests/fixtures/refactor_baseline_v4/README.md) не регенерируются
из текущей реализации. Старые v2/v3 данные остаются доступными через утилиты ревизии
`5ee39b9e0cbdf6c05139715b42f5e5deb96880b3` в отдельном checkout; текущий live-сборщик
больше их не принимает. Исторические отчёты и файлы `data/` не изменены.

Аппаратная точность, USB timing и отзывчивость UI после переноса требуют отдельного
прогона на плате; native-тесты и сборка не заменяют эти измерения.
